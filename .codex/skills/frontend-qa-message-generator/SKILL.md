# QA To Agent Message

这个 skill 用于把自然语言 QA 文本整理成 agent 能稳定生成、并可直接返回给前端的结构化消息。

目标不是润色文案，而是把“人能看懂的问答”压缩成“前端容易渲染、agent 容易复用”的统一 JSON。

## 适用场景

- 用户给出一段 `Q:` / `A:` 文本，希望转成 agent 消息
- 已有 FAQ、排查记录、人工客服问答，需要整理成标准 JSON
- 需要把问答结果直接返回前端展示
- 需要把追问、说明、结论统一成一套稳定字段
- 需要让输出格式固定，方便前端渲染，而不是自由发挥

如果用户主要是要写 playbook、改代码、设计协议，不要用这个 skill。

## 输出目标

默认只输出一个 JSON 对象，不要输出 Markdown 代码块，不要补额外解释。

默认输出结构：

```json
{
  "type": "qa_message",
  "question": "",
  "answer": "",
  "steps": [],
  "conclusion": "",
  "follow_up_questions": []
}
```

字段含义：

- `type`
  - 固定为 `qa_message`
- `question`
  - 用户问题或场景现象的简洁表述
- `answer`
  - 面向前端直接展示的一段短回答
- `steps`
  - 可选，整理出的处理步骤、判断依据或操作顺序
- `conclusion`
  - 可选，最终结论、建议或处理结果
- `follow_up_questions`
  - 可选，如果当前 QA 本质上仍需继续追问，把要补充的问题写在这里

如果某个字段没有内容，优先使用空字符串或空数组，不要自造新字段。

## 转换规则

1. 先抽取最小展示单元
- `question` 写用户在问什么
- `answer` 写最值得直接展示给前端的一段回答
- `steps` / `conclusion` / `follow_up_questions` 按需补充

2. 保留事实，不补编
- 只使用输入里已经出现的事实、结论、限制条件
- 不要脑补未给出的工具名、日志、接口名、实验结果

3. 统一问题表述
- 把用户原始现象压缩成一句简洁的“问题”
- 去掉寒暄、重复、无关背景

4. 整理排查过程
- 把回答里的判断依据、检查步骤、观察结果整理到 `steps`
- `steps` 每项都应是简短独立句子，适合前端列表展示
- 不要暴露内部推理草稿

5. 提炼结论
- 结论写入 `conclusion`
- 只写最终判断、建议或下一步
- 不重复大段过程描述

6. 追问要可展示
- 如果当前答案本质上仍在要信息，把问题写入 `follow_up_questions`
- 每个问题都应面向前端用户，能直接阅读和回复
- 不再要求输出后端专用的 `clarify` / `final` 协议

## 推荐工作流

1. 先清理 QA 文本
- 去掉寒暄、重复句、明显无关内容
- 合并同义问题和重复答案

2. 先判断问题是否已存在
- 如果当前任务会落库到 `doc/qa.md` 或同类 QA 文档，先查找是否已经有同一个问题
- “同一个问题”优先按问题语义判断，不要求问句字面完全一致
- 如果只是同一问题的补充信息、更新结论、修正步骤，视为更新已有条目，不要在文档末尾再次追加一条近似问题

3. 再映射到固定字段
- 所有输出都落到同一个 `qa_message` 结构
- 根据内容决定哪些字段留空，哪些字段填写

4. 如果需要写入 QA 文档，按更新优先
- 已存在问题：
  - 只更新对应条目的 `answer`、`steps`、`conclusion`、`follow_up_questions` 等内容
  - 保持原条目的位置，不要为了补充新信息而在后面重复新增
- 不存在问题：
  - 再新增一个新条目
- 更新时优先合并和替换过时内容，不要把新旧两个版本都保留下来造成重复

5. 最后做协议对齐检查
- 是否是单个 JSON 对象
- 是否没有 Markdown 代码块
- `type` 是否固定为 `qa_message`
- `question` / `answer` 是否可直接展示
- 列表类字段是否使用数组

6. 维护 `doc/qa.md`
- 默认目标是让 `doc/qa.md` 保持“每个问题只有一个当前版本”
- 未命中已有问题时，才允许新增条目
- 命中已有问题时，直接修改对应内容，不做尾部增量追加

## 默认映射

### 适合写入 `follow_up_questions` 的典型信号

- “请确认”
- “还需要补充”
- “麻烦提供”
- “先看一下”
- “是否方便告知”

### 适合写入 `conclusion` 的典型信号

- “初步判断”
- “定位为”
- “原因是”
- “建议处理”
- “结论是”

## 参考

需要样例时，读取 [references/examples.md](references/examples.md)。

如果用户已经给了前端字段约束、TS 类型或接口 schema，优先对齐用户提供的格式；没有的话，默认使用本 skill 定义的 `qa_message` 结构。

## 质量检查

交付前至少自查这些点：

- 是否只输出一个 JSON 对象
- 是否没有额外解释文字
- 是否没有编造输入中不存在的信息
- `question` 和 `answer` 是否适合直接给前端展示
- `steps` 和 `follow_up_questions` 是否为数组
- `conclusion` 是否足够短、清楚、可直接展示
- 如果写入 `doc/qa.md`，是否先查重
- 对已存在问题是否执行了“更新原条目”而不是“尾部追加一条近似内容”
